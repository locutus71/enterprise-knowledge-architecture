Das Problem

Jedes KI-System vergisst. Jede neue Session startet bei null. Kontext geht verloren, Fehler wiederholen sich, Wissen zerfällt. Die Frage ist nicht ob man ein Memory-System braucht, sondern wie man eins baut, das sich selbst verbessert.

🧠

Context-Amnesie

LLMs haben ein begrenztes Kontextfenster. Nach 200k Tokens wird komprimiert oder abgeschnitten. Alles was vorher war: weg.

Jede Session betroffen
🔄

Wiederholungsfehler

Ohne persistentes Gedächtnis macht das System denselben Fehler dreimal. Derselbe Workaround, derselbe Debugging-Pfad, dasselbe Ergebnis.

Produktivitätskiller
📉

Wissensverfall

Recherche-Ergebnisse von letzter Woche? Nicht mehr da. Entscheidungsgrundlagen von letztem Monat? Verloren. Das System wird nicht schlauer, es bleibt gleich.

Kein Compound Effect

Self-Improving

3-Layer Memory

Drei Speicherschichten mit unterschiedlichen Geschwindigkeiten, Kapazitäten und Aufgaben. Wie L1/L2/L3-Cache in einer CPU, aber für Wissen.

Layer 1: Hot Memory
Strukturierte Key-Value-Fakten · Sofort verfügbar · Automatisch injiziert
<1ms
Layer 2: Deep Storage
Destilliertes Wissen · Recherchen, Entscheidungen, Fehler · FTS5-Volltext
~10ms
Layer 3: Semantic Search
Hybrid Search über alle Dokumente · Vector + BM25 · Temporal Decay
~100ms

Layer 1: Hot Memory

Key-Value-Store für aktuelle Zustands-Fakten. IP-Adressen, Projektstatus, Stakeholder-Rollen. Wird bei jedem Session-Start automatisch in den Kontext geladen. Keine Suche nötig, immer da.

# Beispiel Hot Memory Einträge
sandbox_status = "noch nicht eingereicht"
ki_budget_phase1 = 55 # EUR/Monat
naechster_termin = "2026-03-27 JF"
Immer geladen · Kein Query nötig

Layer 2: Deep Storage

SQLite-Datenbank mit 8 Tabellen. Notes, Logs, Snippets, Configs, Relationen, Changelog. FTS5-Volltextsuche. Hier landet alles was aus Sessions destilliert wird: Erkenntnisse, Debugging-Lösungen, strategische Entscheidungen.

# Typische Queries
search "Hybrid Search Konfiguration"
list --type note --project "Architektur"
add note --title "Temporal Decay Formel"
Strukturiert · Durchsuchbar · Versioniert

Layer 3: Semantic Search

Hybrid Search Engine über alle Projektdokumente. Kombiniert Vector-Embeddings (multilingual-e5-base, 768 Dimensionen) mit BM25-Keyword-Search. Temporal Decay sorgt dafür, dass aktuelle Dokumente bevorzugt werden. 25.000+ Chunks aus 400+ Dateien indexiert.

Vector Search (70%)
Versteht Bedeutung. "Kostenanalyse" findet auch "Budget-Vergleich".
BM25 Search (30%)
Exakte Begriffe. "BM25-IDF" findet genau das, nicht Synonyme.
Phrase Bonus
Zusammenhängende Begriffe werden hochgewertet. Keine Wort-Suppe.

"Der Fehler den alle machen: Ein Vector Store für alles. Das ist wie wenn du dein Telefon, deinen Kalender und dein Archiv in eine einzige Schublade wirfst."

Architektur-Entscheidung nach 3 gescheiterten Prototypen

Hybrid Search

Pure Vector Search klingt elegant, funktioniert aber nicht für Enterprise-Wissen. Fachbegriffe, Abkürzungen, exakte Formulierungen gehen verloren. Die Lösung: Zwei Suchverfahren kombiniert, gewichtet, mit Zeitfaktor.

Kriterium Pure Vector Pure BM25 Hybrid (diese Architektur)
Semantisches Verständnis Stark Keins Stark (via Vector-Anteil)
Exakte Fachbegriffe Schwach Stark Stark (via BM25-Anteil)
Multilinguale Suche Ja (e5-base) Nein Ja
Aktualität beachten Nein Nein Ja (Temporal Decay)
Phrase-Awareness Begrenzt Nein Ja (Phrase Bonus)

Temporal Decay

Nicht jedes Dokument altert gleich. Ein Strategiepapier von letzter Woche ist relevanter als eins von vor 6 Monaten. Aber eine Grundsatzentscheidung bleibt immer relevant.

Exponentieller Decay

score = relevance × e(-λ × age_days)
# Halbwertszeit: 90 Tage
# Nach 90 Tagen: 50% Gewicht
# Nach 180 Tagen: 25% Gewicht
# Nach 360 Tagen: 6% Gewicht

Evergreen-Ausnahmen

Bestimmte Dokumenttypen sind zeitlos und werden vom Decay ausgenommen:

  • Grundsatzentscheidungen
  • Architektur-Dokumentation
  • Corporate Design Regeln
  • Organisationsstrukturen
Kein Decay · Immer 100%

Session Start Hook

Lädt bei jedem Gespräch automatisch: Hot Memory Fakten, aktuelle Ziele, offene Fehler (Buglist), Statistiken aus Deep Storage. Der Agent startet nie bei null.

Automatisch · Keine manuelle Aktion

User Prompt Hook

Jede Nachricht des Users bekommt automatisch einen Timestamp mit Wochentag und Uhrzeit. Der Agent kann Zeitabstände berechnen, Arbeitsrhythmen erkennen, exakte Uhrzeiten in Logs dokumentieren. Grundlage fuer zeitbasiertes Coaching.

Zeitbewusstsein · Muster-Erkennung

Pre-Tool Hooks

Fangen ab bevor etwas passiert. Email-Versand ohne Freigabe? Blockiert. Datei löschen? Blockiert. Destruktive Git-Operationen? Warnung. Policy as Code.

Safety Layer · Kein Undo nötig

Pre-Compact Hook

Wenn das Kontextfenster voll wird, komprimiert das System automatisch. Vorher: Alles Wichtige wird in Deep Storage geschrieben. Kein Wissensverlust durch Komprimierung.

Focus Loop Pattern

Session Stop Hook

Bei Session-Ende: Zusammenfassung schreiben, Wissen exportieren, Reindex der Search Engine triggern. Die nächste Session profitiert automatisch.

Validation Layer

Zero Trust auf Agent-Wissen. Jede Information die persistent wird, muss 6 Gates passieren. Weil falsches Wissen mit vollem Gewicht gespeichert wird, wenn man es nicht validiert.

1

Source Pinning

Jeder Fakt braucht eine nachprüfbare Quelle. Kein "laut verschiedenen Quellen". Konkrete URL, Datei, oder Zitat.

2

Existence Check

Bevor eine Funktion, Datei oder API empfohlen wird: Existiert sie noch? Simpler String-Match, kein LLM nötig. Verhindert Halluzinationen über gelöschte Ressourcen.

3

Keyword Cross-Check

Stimmen die Fachbegriffe? Heisst es "Betriebsvereinbarung" oder "Betriebsverordnung"? Ein falscher Begriff in einem Governance-Dokument kann fatale Folgen haben.

4

Contradiction Check

Widerspricht die neue Information bestehenden Fakten im Hot Memory oder Deep Storage? Wenn ja: Nicht überschreiben, sondern flaggen.

5

Confidence Score

Wie sicher ist die Quelle? Verifiziert (Primärquelle) > Agent-generiert (LLM-Output) > Inferiert (Schlussfolgerung). Niedrige Confidence = Review erforderlich.

6

Export Filter

Beim Export aus Deep Storage in die Search Engine: Rejected Notes werden gefiltert, veraltete Einträge markiert, Duplikate entfernt.

Knowledge Loop

Der Mechanismus der eigenständigen Weiterentwicklung. Jede Session macht das System besser. Nicht weil jemand es trainiert, sondern weil die Architektur Lernen erzwingt.

Wie es funktioniert

Am Ende jeder Session wird destilliert: Was wurde gelernt? Welche Fehler wurden gemacht? Welche Entscheidungen getroffen? Das Ergebnis geht in Deep Storage. Ein Export-Script wandelt Notes in durchsuchbare Dokumente um. Die Search Engine reindexiert. Die nächste Session hat automatisch mehr Kontext.

Warum es funktioniert

Weil es nicht optional ist. Hooks erzwingen das Speichern. Pre-Compact sichert vor Kontextverlust. Session-Stop triggert den Export. Das System vergisst nicht, weil das Vergessen architektonisch verhindert wird.

Lessons Learned

Was nicht funktioniert hat, ist wertvoller als was funktioniert. Hier sind die teuren Erkenntnisse aus 6 Monaten Entwicklung.

❌

"Ein Vector Store reicht"

Drei Prototypen gebaut, alle mit reiner Vector Search. Fachbegriffe gingen verloren, Abkürzungen wurden nicht gefunden, aktuelle Dokumente hatten kein höheres Gewicht als veraltete. Die Lösung war nicht ein besseres Embedding-Modell, sondern ein komplett anderer Ansatz: Hybrid.

❌

"LLMs validieren sich selbst"

Falsch. Ein LLM das seine eigenen Aussagen prüft, bestätigt sich selbst. Validation braucht externe Checks: Existiert die Datei? Stimmt der Fachbegriff? Widerspricht das dem bestehenden Wissen? Erst als die 6 Gates implementiert waren, sank die Fehlerquote messbar.

❌

"Cloud-First ist immer besser"

Für Klassifikation und Routing ist ein lokales 3B-Modell schneller, billiger und datenschutzkonformer als ein API-Call. Die Erkenntnis: Cloud für Komplexes, lokal für Schnelles. Nicht entweder-oder, sondern beides strategisch einsetzen.

❌

"Mehr Kontext = bessere Antworten"

200k Token Kontextfenster vollstopfen macht Antworten nicht besser, sondern langsamer und teurer. Die Lösung: Schichtung. Nur das Nötigste automatisch laden (Hot Memory), den Rest on-demand suchen (Deep Storage + Semantic Search).

❌

"Theoretische Frameworks beeindrucken"

Content-Validierung via LinkedIn: Ein Post über theoretische KI-Frameworks bekam 40 Impressions. Ein Post über konkrete Architektur-Erkenntnisse bekam 1.755+. Praxis schlägt Theorie 24:1. Immer.

✅

"Policy as Code statt Dokumentation"

Regeln in Dokumenten werden vergessen. Regeln als Hooks werden erzwungen. Email-Versand ohne Freigabe? Automatisch blockiert. Datei löschen? Hook verhindert es. Das System braucht keine Disziplin, weil die Architektur Fehler verhindert.

Offene Challenges

Kein System ist fertig. Diese Probleme sind noch nicht gelöst. Transparenz über offene Flanken ist wichtiger als der Anschein von Perfektion.

Single Point of Failure

Das gesamte System läuft auf einer Maschine. Kein Backup-Server, kein Failover. Ein Hardware-Ausfall bedeutet Stillstand.

Kritisch

Bus Factor = 1

Eine Person kennt das System. Keine Dokumentation die ausreicht um es zu betreiben. Dieses Dokument ist ein erster Schritt.

Kritisch

Validation noch nicht automatisiert

Die 6 Gates existieren als Konzept und werden manuell angewendet. Eine vollautomatische Pipeline fehlt noch.

In Arbeit

Skalierung unklar

Das System funktioniert für eine Person. Ob und wie es für ein Team skaliert, ist noch nicht getestet. Multi-User-Szenarien sind konzeptionell durchdacht, aber nicht implementiert.

Offen

Embedding-Modell fixiert

multilingual-e5-base funktioniert gut, aber ein Upgrade auf ein besseres Modell würde einen kompletten Reindex erfordern. Hot-Swap ist nicht möglich.

Akzeptiert

Kosten-Monitoring rudimentär

API-Kosten werden nicht systematisch getrackt. Bei steigender Nutzung könnte das zum Problem werden.

Niedrig

Ein Experiment das funktioniert.
